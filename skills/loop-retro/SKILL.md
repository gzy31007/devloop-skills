# loop-retro · 发版与复盘反哺

## 一、发版（Shipping）

仅在 `/loop-review` 给出「全绿放行」且工作树干净时执行发版：

1. **版本号与变更对齐**：核对 `pyproject.toml` / `package.json` / 包入口版本号与本次发布标签一致；在 `FEATURE_MAP.md` 补齐本版新增外部行为与验收入口（删掉已下线的行，保留历史版本号）。
2. **发版前终检**：确认目标提交正是审查通过的候选 SHA（无未审查夹带），必要时复跑一次架构门禁与构建/打包自检，确认无脏文件与端口残留。
3. **合主干与打标签**：
   - 将候选分支快进或干净合并入主干分支，打本地版本标签 `vX.Y`（或预发布标签 `vX.Y-rc1`），回读主干与标签指向同一 SHA。
   - **对外推送闸门**：涉及推公网仓库、发包或正式上线时，先走预发布确认或遵守用户已有明确授权，同时记录回滚命令（如回退标签或恢复上一主干 SHA）。

## 二、复盘与 Learn 反哺（让下一轮 `build` 更稳）

梳理本轮打回原因与漏网风险，按固定优先级沉淀，**同一条教训只落最靠前的一层**：

1. **架构与门禁脚本**：能机械拦住的错误优先写进 `arch_gate.py`、`verify_scripts.py` 或项目静态检查；
2. **行为与属性回归测试**：静态拦不住的错误写进端到端或脏输入属性测试，名字写进 `FEATURE_MAP.md`；
3. **反哺上游技能（Learn）**：
   - 属于通用编码防错的教训，反哺写进 `loop-build` 的「源头防错底线」，让下一轮写代码时直接避坑；
   - 属于通用审查盲区的教训，反哺写进 `loop-review` 与 `references/review-checklist.md`；
   - 若发现的是 `devloop` 套件本身的跨项目流程缺陷，记录标准改进条目供套件仓库统一升级。

## 三、处理过时取舍

逐条核对 `DECISIONS.md` 与当前代码现实：
- 前提仍成立：保留；
- 前提已变化：重写该条，旧条目标记 `[superseded by YYYY-MM-DD 新条目摘要]`；
- 决策已废弃：标记 `[superseded by 废弃原因]`。

## 四、写复盘摘要

在 `.loop/handoff.md` 末尾追加本版复盘：发版标签与 SHA、打回次数（区分环境/脚本类与方法类）、每次根因、已固化的门禁或反哺条目、下一版的减法重构检查点。数字与命令照抄实测输出。

## 五、清理收尾

删除临时目录与测试 worktree，确认工作树干净与端口零残留：

```bash
python skills/loop-review/scripts/reap_and_run.py --status
```
